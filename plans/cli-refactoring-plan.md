# План приведения в порядок app/cli.py

## Контекст

`app/cli.py` — не рудимент: это точка входа `recs` (`pyproject.toml`:
`recs = "app.cli:main"`) и единственная команда, которой запускается GPU-воркер
в проде (`deploy/worker/Dockerfile` CMD: `python -m app.cli worker ...`).
Файл активно используется, удалять/сокращать его не нужно — но у него один
серьёзный структурный дефект.

## Текущее состояние

- Файл: 2122 строки, 28 CLI-команд (`typer`).
- 27 команд (`scan`, `analyze`, `db-check`, `navidrome-*`, `similar`, `stats`
  и т.д.) короткие и линейные — Cognitive Complexity в порядке, трогать их
  не требуется.
- Одна команда — **`worker()`** (`app/cli.py:1139-1818`, ~680 строк) —
  даёт Cognitive Complexity 297 и содержит ещё 3 сложных вложенных замыкания
  (`claim_more`, `process_ready_embedding_batches`, `process_ready_head_batches`),
  которые Sonar считает отдельными "CRITICAL"-функциями внутри того же файла.
- Внутри `worker()` — 7 замыканий с `nonlocal`, делящих общее мутабельное
  состояние (очереди задач, счётчики, буферы результатов) через closure-scope
  вместо явных параметров/атрибутов объекта.

### Обнаруженное дублирование внутри worker()

1. Сборка словаря failure (`task_id/error/error_type/stage/retryable`) — есть
   готовый хелпер `append_worker_failure` (line 1116), но в двух местах
   (~1686, ~1765) он не используется — код продублирован inline.
2. Essentia-fallback после ошибки прямого TensorFlow-бэкенда — идентичный блок
   повторён в `process_ready_embedding_batches` (~1444-1473) и в обработчике
   `done_futures` (~1614-1644).
3. Паттерн `HTTPError 409 → close_inactive_task(...)` повторяется 4+ раза
   почти идентично в разных ветках.

### Тестовое покрытие сейчас

`tests/test_cli.py` — только 2 теста (`worker_failure_retryable`). Внутренняя
логика `claim_more`/буферизации/потоков воркера не покрыта ничем. Это главный
риск: рефакторить 680-строчную функцию, которая крутится на проде без сетки
безопасности.

## Принципы (по аналогии с plans/refactoring-plan.md)

1. Один этап — один коммит, каждый этап должен проходить CI (Test → Sonar →
   Security Scan) без регрессий.
2. Сначала тесты, потом рефакторинг — не наоборот.
3. Ранние этапы — чисто механические (дедупликация без изменения порядка
   операций), логика не меняется. Если на каком-то этапе окажется, что фикс
   меняет поведение — остановиться и обсудить, не решать в одностороннем
   порядке.
4. Крупная структурная перестройка (замыкания → класс) — отдельный этап в
   конце, после того как есть тесты, которые её подтвердят.

## Этапы

### Этап 1 — Тестовая сетка для worker() (сначала, до любых правок)

Написать unit-тесты с мок-сервером (`http.server`/`responses`-стиль заглушка
или monkeypatch `post_json`/`urlopen`) на:

- `claim_more` — claim возвращает задачи → они попадают в `future_to_task`.
- `process_ready_embedding_batches` — накопление патчей до `target_patches`,
  затем один вызов `direct_model.predict_patches_unpadded`.
- `process_ready_head_batches` — аналогично для head-моделей.
- `flush_worker_buffers` / `submit_worker_buffers` — очистка буферов и
  `acknowledged_task_ids` после успешной отправки.
- Essentia-fallback ветка (мок исключения на прямом бэкенде → вызов essentia).
- `close_inactive_task` — 404 и `active=False` оба закрывают задачу.

**Риск:** низкий (только добавление тестов). **Блокирует:** этапы 2-5 не
начинать, пока эти тесты не зелёные в CI.

### Этап 2 — Дедупликация failure-словаря

Заменить два inline-дубликата (~1686, ~1765) вызовом существующего
`append_worker_failure(failures, task_id, exc)`. Поведение идентично —
структура словаря совпадает 1:1.

**Риск:** низкий, чисто механическое.

### Этап 3 — Дедупликация essentia-fallback

Вынести повторяющийся блок (~1444-1473 и ~1614-1644) в отдельную функцию
модуля, например `fallback_to_essentia_embedding(settings, model_name,
gpu_batch_size, audio_path, task, results, failures, completed_task_ids) -> None`,
и вызывать её из обоих мест.

**Риск:** низкий-средний — нужно аккуратно сохранить порядок side-effect'ов
(`append_embedding_result`/`append_worker_failure`/`completed_task_ids.add`/
`typer.echo`) один в один.

### Этап 4 — Дедупликация HTTPError 409 → close_inactive_task

Вынести общий паттерн «если исключение — HTTPError(409), попробовать закрыть
неактивную задачу, иначе — обычная обработка failure» в один хелпер и
использовать во всех 4+ местах.

**Риск:** средний — веток обработки исключений несколько, нужно проверить
каждый call site по отдельности перед заменой.

### Этап 5 — Замер результата

После этапов 2-4 запросить у Sonar Cognitive Complexity по `app/cli.py`
повторно (`mcp__sonarqube__get_component_measures` или
`search_sonar_issues_in_projects` по rule `python:S3776`), сравнить с
исходным 297+3. Ожидание: заметное снижение за счёт сокращения тела функции,
но полной ликвидации CRITICAL, скорее всего, не будет — основной вклад даёт
глубина вложенности closures, а не длина кода.

**Здесь пауза и обсуждение**: смотрим, насколько снизилась сложность, и
решаем, нужен ли этап 6.

### Этап 6 (обсуждается отдельно, только после этапа 5) — Структурная перестройка

Вынести общее состояние `worker()` (очереди, счётчики, буферы, флаг
`draining`) в отдельный класс (например `WorkerRuntime`), а текущие
замыкания — в его методы. Это уберёт `nonlocal` и вложенность, что и есть
основной источник Cognitive Complexity, но:

- Большой дифф на критичном для прода файле (единственная точка входа
  GPU-воркера).
- Не начинать без зелёных тестов из этапа 1 и явного согласия — это
  меняет структуру кода, а не только убирает дублирование.
