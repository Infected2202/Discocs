# План: браузерная буферизация и транскодинг воспроизведения

## Цель

Уменьшить или убрать паузы между треками при нестабильном мобильном интернете:

- текущий трек должен продолжать загружаться браузером до полного буфера;
- только после полного буфера текущего трека браузер начинает загружать следующий трек очереди;
- полностью загруженный следующий трек хранится в браузере как `Blob` и при переключении воспроизводится через локальный `blob:` URL;
- пользователь может включить транскодинг Navidrome и выбрать целевой bitrate, чтобы уменьшить объём передаваемых данных.

Речь идёт о данных на клиентском устройстве. Дисковый аудиокеш backend в эту задачу не входит.

## Текущее состояние

- `ui/src/engine/AudioEngine.ts` использует один `HTMLAudioElement` с `preload="none"`.
- При `load()` старый элемент освобождается, новый трек начинает сетевую загрузку с нуля.
- `buffered` отражает только нативные `TimeRanges` текущего элемента; переиспользуемой копии трека нет.
- `ui/src/store/playerStore.ts` выбирает следующий трек только при `ended`, skip или ручном переходе.
- `GET /api/v1/tracks/{track_id}/audio` проксирует `Navidrome /rest/stream.view` только с `id`, без параметров транскодинга.
- Персональные настройки уже хранятся в generic-таблице `user_settings`; новая миграция БД не требуется.

## Принятые решения

1. Буферизация реализуется в новом UI (`ui/src/`), старая админка `app/ui.html` не меняется.
2. Текущий трек получает `preload="auto"`.
3. Полный буфер определяется по `HTMLMediaElement.buffered`, а не по событию `canplaythrough`.
4. Следующий трек загружается явным `fetch(...).blob()`. Это гарантирует наличие полного тела ответа в браузере перед использованием `blob:` URL.
5. Одновременно хранится не более одного подготовленного следующего трека и текущего Blob, если он был подготовлен ранее.
6. При изменении следующего элемента очереди ненужный prefetch отменяется через `AbortController`.
7. Если переход произошёл до завершения prefetch, плеер немедленно использует обычный сетевой URL и не ждёт Blob.
8. Транскодинг — персональная настройка пользователя. Первая версия использует MP3 и варианты `96/128/192/256/320` Кбит/с.
9. Выключенный транскодинг явно запрашивает `format=raw`; включённый — `format=mp3`, `maxBitRate=<quality>` и `estimateContentLength=true`.
10. Изменение профиля транскодинга инвалидирует незавершённый и готовый prefetch: Blob другого качества повторно не используется.

## Ограничение браузерной модели

`preload="auto"` является подсказкой браузеру, поэтому первый открытый трек не во всех мобильных браузерах гарантированно будет скачан целиком заранее. Явный `fetch().blob()` применяется к следующему треку и гарантирует его полную готовность. Если браузер не довёл нативный буфер текущего трека до конца, prefetch следующего по принятому правилу не стартует.

Не добавлять параллельный `fetch()` текущего трека: это дублировало бы трафик на мобильном соединении. Service Worker/MediaSource для единого принудительного потока значительно усложнят Range, seek и поддержку контейнеров и не входят в первую версию.

## Состояния клиентского аудиобуфера

В `AudioEngine` ввести внутреннее состояние:

```ts
type PlaybackProfile = {
  transcodingEnabled: boolean
  bitrateKbps: 96 | 128 | 192 | 256 | 320
  key: string // raw или mp3-192 и т.п.
}

type PrefetchedAudio = {
  trackId: number
  profileKey: string
  blob: Blob
  objectUrl: string
}
```

Дополнительно хранить:

- активный `trackId` и `profileKey`;
- Blob/Object URL активного трека, если он пришёл из prefetch;
- один готовый `PrefetchedAudio`;
- идентификатор текущей prefetch-цели;
- `AbortController` выполняющегося prefetch;
- признак, что событие полного буфера для текущего source уже было отправлено.

Object URL освобождается только после того, как соответствующий трек перестал быть активным. Все оставшиеся URL и запросы освобождаются при logout/reset.

## Этап 1. Контракт персональных настроек транскодинга

### Backend

Расширить `UserSettingsPatchRequest`:

```json
{
  "transcoding_enabled": true,
  "transcoding_bitrate_kbps": 192
}
```

Требования:

- `transcoding_enabled`: optional boolean;
- `transcoding_bitrate_kbps`: optional enum `96 | 128 | 192 | 256 | 320`;
- default: `false` и `192`;
- API возвращает типизированные boolean/number, хотя generic store сохраняет канонические строки;
- неизвестные поля по-прежнему запрещены;
- частичный PATCH не сбрасывает второе поле.

Обновить:

- `app/schemas/requests.py`;
- `app/store/settings.py`;
- `app/api/settings.py`;
- `tests/test_user_settings.py` и/или API-тесты настроек.

### Frontend

Расширить `UserSettings` в `ui/src/api/settings.ts` и существующие query/mutation hooks.

Добавить в `ui/src/pages/SettingsPage.tsx` секцию «Воспроизведение»:

- свитч «Транскодирование»;
- select качества;
- пояснение, что меньший bitrate уменьшает трафик и помогает на мобильной сети;
- select disabled при выключенном свитче;
- сохранение через `/api/v1/me/settings`;
- состояния загрузки, сохранения и ошибки;
- русские и английские строки в namespace `settings`.

Критерий готовности этапа:

- настройки проходят round-trip для разных пользователей;
- UI показывает сохранённые значения после перезагрузки;
- переключение и bitrate покрыты компонентными тестами.

## Этап 2. Параметры транскодинга в аудиопотоке

Изменить формирование URL Navidrome в `app/api/tracks.py`:

- disabled: `stream.view?id=<id>&format=raw`;
- enabled: `stream.view?id=<id>&format=mp3&maxBitRate=<bitrate>&estimateContentLength=true`.

Настройки берутся из персонального `user_settings` активного запроса. Клиент не должен иметь возможность передать произвольный формат или bitrate в Navidrome.

Одновременно перевести интерактивный аудиопоток на credentials активной пользовательской сессии, как уже сделано для других интерактивных операций Navidrome. Глобальные service credentials не должны определять доступ к пользовательскому playback.

Обеспечить различимость playback profile в URL, который получает браузер. `trackAudioUrl` должен включать стабильный непарольный ключ профиля, например:

```text
/api/v1/tracks/42/audio?profile=raw
/api/v1/tracks/42/audio?profile=mp3-192
```

Backend валидирует ключ против сохранённых настроек пользователя; ключ нужен для корректной идентичности browser source и Blob, а не как источник доверенных настроек.

Тесты:

- выключенный режим добавляет `format=raw`;
- каждый разрешённый bitrate добавляет ожидаемые параметры;
- неизвестный/несовпадающий profile не позволяет обойти настройки;
- Range и HEAD продолжают проксироваться;
- ошибки Navidrome сохраняют текущий API-контракт;
- используются credentials активного пользователя.

Критерий готовности этапа: обычное и транскодированное воспроизведение проходят через тот же `/audio` endpoint, а существующие seek/Range-сценарии не регрессируют.

## Этап 3. Надёжное определение полного буфера текущего трека

В `AudioEngine`:

1. Заменить `preload="none"` на `preload="auto"`.
2. Сохранить текущий расчёт отображаемой доли `buffered`.
3. Добавить отдельный callback `onFullyBuffered(trackId, profileKey)`.
4. Проверять покрытие всего временного диапазона `0..duration` объединением `TimeRanges`, а не только конец диапазона около `currentTime`.
5. Разрешить небольшой допуск к duration (например, 0.25 секунды) из-за округлений контейнера.
6. Проверять состояние на `progress`, `loadedmetadata`, `durationchange` и `canplaythrough`.
7. Отправлять callback не более одного раза для конкретного source.
8. Сбрасывать признак при загрузке нового source.

Не считать `canplaythrough` эквивалентом полной загрузки: оно означает прогноз непрерывного воспроизведения, а не наличие всего файла.

Тесты `AudioEngine.test.ts`:

- один диапазон покрывает весь трек;
- несколько смежных диапазонов вместе покрывают трек;
- разрыв в диапазонах не считается полным буфером;
- буфер только вокруг текущей позиции не считается полным;
- учитывается допуск к duration;
- callback не дублируется;
- новый `load()` сбрасывает состояние.

## Этап 4. Явный prefetch следующего трека в Blob

Добавить в `AudioEngine` или отдельный `BrowserAudioBuffer` методы с явным lifecycle:

```ts
prefetch(trackId: number, url: string, profileKey: string): Promise<void>
consumePrefetched(trackId: number, profileKey: string): string | null
cancelPrefetch(): void
clearPrefetched(): void
```

Поведение `prefetch`:

- использовать `fetch(url, { credentials: "same-origin", signal })`;
- проверять `response.ok`;
- читать ответ через `response.blob()`;
- не заменять готовый актуальный Blob повторной загрузкой;
- после загрузки ещё раз проверять, что цель очереди и profile не изменились;
- создавать `URL.createObjectURL(blob)` только для актуального результата;
- ошибки сети и abort не переводят основной плеер в `error`;
- журналировать start/complete/cancel/failure через существующий player logger без URL с секретами.

Поведение при воспроизведении:

- если `trackId + profileKey` совпадают с готовым Blob, использовать `blob:` URL;
- иначе использовать обычный `/audio` URL немедленно;
- Blob становится активным и не освобождается до ухода с трека;
- после ухода с трека активный object URL отзывается.

Тесты:

- успешный fetch создаёт и затем отдаёт object URL;
- несовпадающий track/profile не использует Blob;
- повторный запрос той же цели не дублирует fetch;
- смена цели abort-ит старый запрос;
- устаревший завершившийся Promise не перезаписывает новый результат;
- HTTP error не ломает текущее воспроизведение;
- object URL освобождается ровно после использования;
- `clear()` освобождает URL и отменяет запрос.

## Этап 5. Связь prefetch с очередью плеера

В `playerStore` добавить координацию без хранения Blob в Zustand state:

1. После `onFullyBuffered` вычислить фактический следующий `QueueItem` после `currentQueueItemId`.
2. Не делать prefetch при `repeat_mode === "one"`.
3. Если следующего элемента нет, ничего не загружать; autoplay refill сначала должен добавить его в очередь.
4. После любого изменения очереди пересчитать цель:
   - если текущий ещё не полностью buffered — только отменить устаревшую загрузку;
   - если полностью buffered — отменить старую цель и начать новую.
5. Учитывать:
   - normal end;
   - skip next/previous;
   - jump по очереди;
   - play next;
   - shuffle;
   - autoplay/Flow refill;
   - ручную замену playback source;
   - восстановление сессии;
   - logout.
6. При `playTrack` сначала попытаться `consumePrefetched`; при отсутствии результата использовать network URL.
7. После перехода новый текущий Blob уже полностью локален, поэтому следующий prefetch можно запускать сразу после успешного старта, не ожидая дополнительного `progress`.

Последний пункт важен: трек, запущенный из готового Blob, по определению полностью доступен браузеру.

Тесты `playerStore`:

- prefetch начинается только после полного буфера текущего;
- выбирается именно следующий queue item;
- готовый Blob используется при `ended`;
- ранний skip не ждёт незавершённый Blob;
- изменение очереди меняет prefetch target;
- shuffle и jump не оставляют старую цель;
- repeat-one не загружает следующий трек;
- autoplay refill может запустить prefetch после появления следующего item;
- смена bitrate отменяет старый prefetch;
- logout очищает все клиентские аудиоданные.

## Этап 6. UX и диагностика

Первая версия не требует отдельного пользовательского индикатора для следующего трека. Существующий индикатор `buffered` продолжает показывать только активный трек.

Добавить диагностические сообщения:

- current fully buffered;
- next prefetch started/completed/cancelled/failed;
- prefetched Blob consumed;
- fallback to network source;
- playback profile changed.

Не логировать session cookies, Navidrome token/salt/password или полный upstream URL.

Опционально после стабилизации можно добавить небольшой статус «Следующий трек загружен», но это не блокирует первую версию.

## Этап 7. Документация

Обновить документацию в `docs/`:

- архитектура browser buffering и lifecycle Blob;
- настройки транскодинга и значения bitrate;
- требования к transcoding profile в Navidrome;
- поведение fallback при раннем переключении;
- ограничение `preload="auto"` для первого трека;

Не документировать серверный аудиокеш, так как он не является частью решения.

## Критерии готовности

Фича считается завершённой, когда:

- при полном буфере текущего трека браузер начинает единственную загрузку следующего;
- полностью загруженный следующий трек воспроизводится из `blob:` URL;
- переход на готовый трек не делает новый `/audio` запрос;
- ранний переход не блокируется ожиданием prefetch;
- изменения очереди и настроек корректно отменяют устаревшие загрузки;
- в браузере одновременно не накапливается неограниченное число Blob;
- object URL и запросы освобождаются при смене source и logout;
- транскодинг можно включить и выбрать допустимый bitrate в новом UI;
- Navidrome получает только валидированные параметры текущего пользователя;
- raw playback, Range, seek, restore session, autoplay и Flow не регрессируют;
- backend/frontend тесты покрывают ключевые ветки и падают при удалении реализованной логики;
- документация обновлена;
- Jenkins и SonarQube завершаются успешно.

## Вне scope первой версии

- серверный дисковый аудиокеш;
- офлайн-прослушивание и постоянное хранение музыки между сессиями браузера;
- Cache Storage/Service Worker;
- IndexedDB/OPFS для аудиофайлов;
- MediaSource и самостоятельная сборка потоков по чанкам;
- несколько заранее загружаемых следующих треков;
- адаптивное автоматическое качество по Network Information API;
- выбор кодека пользователем;
- HLS и adaptive bitrate streaming;
- отдельный лимит дискового кеша Navidrome.

## Возможное развитие после первой версии

После измерений на реальных мобильных сетях отдельно оценить:

- начинать ли prefetch немного раньше 100% буфера текущего трека;
- нужен ли device-specific bitrate вместо общей настройки пользователя;
- стоит ли сохранять один Blob предыдущего трека для мгновенного Previous;
- нужен ли Service Worker для гарантированной полной загрузки самого первого трека без двойного трафика;
- нужен ли автоматический выбор `96/128/192` по фактической скорости загрузки.
