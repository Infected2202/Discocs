## ⚠️ Доктрина: этот список НЕ полон

Перечень точек доработки ниже (§1–§11) — **не исчерпывающий и не будет таким**.
Приложение большое, персональное измерение протекает в неочевидные места
(кэши, глобальное in-memory состояние, персистенс на фронте, чужие строки).
Часть таких мест мы уже нашли постфактум (см. §11) — значит есть и те, что
всплывут **только при реализации**. Это ожидаемо, не признак плохого плана.

**Правило: при каждом касании кода задавать вопрос «а это персональное?».**
Практические эвристики (default-deny по данным):

1. **Любой SQL к персональной таблице без `user_id` — баг.** Preference,
   playback, flow, mixes, playlists, instant-mix — фильтр по юзеру обязателен;
   пропуск = утечка чужих данных.
2. **Любой кэш/глобальное состояние** (`app/state.py`, `albums_for_you_cache`,
   любые `dict`-кэши по ключу) — спросить: ключ включает `user_id`? Если в
   значении персональные данные, а ключ общий — утечка между юзерами.
3. **Любая персональная строка** — проверить, не зашита ли она в **общую**
   таблицу (как `release_aggregates.preference_summary_json`). Аудио-производное
   общее, поведенческое — личное; в одной строке их мешать нельзя.
4. **Любой ответ API** — спросить: увидит ли его другой юзер? Кэшируем ли его
   общий прокси (`Cache-Control`)?
5. **Любой фронт-персистенс** (localStorage, zustand `persist`, react-query
   кэш) — переживает ли он смену аккаунта на том же браузере? Logout обязан
   всё персональное очищать.
6. **Исключения-агрегаты** (например, публичный `SUM(play_count)` на стр.
   артиста) — держать отдельно и осознанно, не путать «моё» и «общее».

**Тест-инвариант на каждый персональный эндпоинт:** «юзер A не видит данные
юзера B и наоборот». Гонять как регресс — это дешёвый детектор пропущенной
фильтрации.

**§11 — живой список.** Всё новое, найденное при реализации, дописывать туда
(и в этот раздел, если всплывает новый класс проблемы).

## Цель

Сейчас discocs — одно-пользовательское приложение. Планируется хостинг: люди
с доступом заходят под своим логином, у каждого — **персональные
рекомендации** (лайки, история, flow, миксы, дашборд). Общая часть —
музыкальный каталог и его анализ (треки, релизы, артисты, эмбеддинги, HNSW-
индекс) — остаётся единой на всех.

Фаза 1 (гейт доступа, `docs/auth.md`) уже впускает по логину Navidrome, но
**все данные общие**: `request.state.principal` ставится в middleware и **никем
не читается для фильтрации** (проверено grep'ом: `principal` встречается только
в `auth_middleware.py` — установка, и `cli.py` — вне API-скоупинга; ни один
персональный роутер его не читает).

## Что общее, а что персональное

|---|---|---|

| Анализ | `embeddings`, `release_embeddings`, `track_predictions`, `track_features`, `release_aggregates` (audio-часть) | **Общий** |
| Индекс | `data/index_*_hnsw.bin` | **Общий** |
| Предпочтения | `user_track_preferences`, `user_release_preferences`, `user_artist_preferences` | **Per-user** |
| События | `playback_events`, `playback_sessions`, `queue_items` | **Per-user** |
| Flow | `flow_profiles`, `flow_regions`, `flow_region_tracks`, `flow_region_embeddings`, `flow_generation_runs` | **Per-user** |
| Миксы | `generated_mixes`, `generated_mix_items` | **Per-user** |
| Плейлисты | `playlists`, `playlist_items` | **Per-user, владелец + visibility** (см. §9) |
| Инстант-микс лог | `instant_mix_requests` | **Per-user** (или аноним. телеметрия?) |
| Кэш | `albums_for_you_cache`, `release_aggregates.preference_summary_json` | **Per-user** (ключ включает user_id) |
| Фидбек | `feedback` | **Общий** (eval-сигнал качества, не личный вкус — §Решено) |

Ключевой водораздел: **аудио-производные (эмбеддинги, фичи, центроиды релизов)
общие; всё, что зависит от поведения человека — персональное.**

### Исключение: глобальные агрегаты по всем юзерам  ✅ РЕАЛИЗОВАНО

Некоторые счётчики, хоть и выведены из персонального поведения, показываются
**публично и суммируются по всем пользователям**:

- **Счётчик прослушиваний на странице артиста** — сумма play_count по всем
  юзерам, виден всем. Т.е. `user_artist_preferences` остаётся per-user (PK
  `(user_id, artist_id)`), но для страницы артиста нужен **отдельный
  агрегат-запрос** `SUM(play_count) GROUP BY artist_id` (или материализованный
  глобальный счётчик). Аналогично может понадобиться для треков/релизов —
  ❓уточнить объём: только артист, или ещё трек/релиз.

Вывод: per-user хранение НЕ мешает публичным агрегатам — они читаются
`SUM(...)` поверх всех строк. Важно не перепутать «мой play_count» (для моих
рекомендаций) и «общий play_count» (для витрины артиста).

## Ядро рекомендаций почти не трогаем

`app/recommender.py` — чисто контентный поиск по эмбеддингам (HNSW cosine),
**без пользовательского измерения**. Он не меняется. Персонализация целиком
живёт в *слоях над ним*: предпочтения → flow-профили → генерация миксов →
autoplay → дашборд-шелфы. Именно эти слои и надо скоупить по пользователю.

## Точки доработки

### 1. Личность и модель пользователя  ✅ РЕШЕНО

**Решение:** свой внутренний `user_id` (int) + маппинг на Navidrome username.
Личность = логин/пароль Navidrome, введённые при входе (как в Фазе 1).

- Новая таблица `users`: `id` (внутренний int), `navidrome_username`
  (unique), `created_at`, `last_login_at`. Роль/админ-флаг **не нужен** (см. §8).
- Логин уже верифицирует креды Navidrome (`app/auth.py`). При успехе:
  upsert `users` по `navidrome_username` → получаем `user_id`, привязываем к
  сессии. Таблица `sessions` уже хранит `username`; добавить `user_id` (или
  резолвить через `users` на каждый запрос).
- `resolve_session` → возвращает не только username, а `(user_id, username)`.
  Middleware кладёт `request.state.user_id`.
- Свой int-id переживёт переименование в Navidrome и чище как FK во всех
  персональных таблицах.

### 2. Схема БД: добавить `user_id`

Во все «персональные» таблицы (см. таблицу выше) добавить `user_id`:

- Preference-таблицы: PK меняется с `track_id` на `(user_id, track_id)` (и
  аналогично release/artist). Это **смена PK**, а не `_ensure_column` —
  нужна аккуратная миграция (создать новую таблицу, перелить, переименовать),
  т.к. проект использует `CREATE TABLE IF NOT EXISTS` + `_ensure_column` без
  версионированных миграций (`docs/data-model.md`).
- `playback_events`, `playback_sessions`, `flow_profiles`, `generated_mixes`,
  `playlists`, `instant_mix_requests`: добавить колонку `user_id` + индексы.
- `flow_profiles`: уникальность была по `model_key`; станет
  `(user_id, model_key)`.
- `albums_for_you_cache`: PK `model_name` → `(user_id, model_name)`.
- **Миграция существующих данных**: всё текущее содержимое принадлежит одному
  человеку (Саня) → назначить `user_id` owner-пользователя.

#### Контракт owner-миграции  ✅ РЕШЕНО

Owner задаётся env `DISCOCS_OWNER_USER` (= navidrome_username). Правила, чтобы
не осиротить историю Сани при первом апгрейде:

- Миграция сначала **upsert'ит owner в `users`** и резолвит `user_id`.
- Если env **не задан или не резолвится** — миграция **падает громко** (raise,
  а не default), НЕ оставляет `user_id = NULL` и не продолжает. Осиротевшие
  персональные строки = молчаливая потеря профиля, недопустимо.
- Все существующие персональные строки получают `user_id` owner'а в той же
  транзакции, что и смена PK.

#### Безопасность миграции PK (самое опасное место)

Проект без версионированных миграций (`CREATE TABLE IF NOT EXISTS` +
`_ensure_column`, `docs/data-model.md`). Смена PK `track_id → (user_id,
track_id)` — это create-new-table / copy / rename на **живой БД Сани**.
Обязательные предохранители:

1. **Бэкап `data/app.db`** перед миграцией — часть процедуры, не «само собой».
2. **Идемпотентность**: повторный старт не должен падать/дублировать
   (при `IF NOT EXISTS`-подходе это легко проглядеть — миграция должна
   определять, что уже применена).
3. **Эвакуационный тест**: снять снимок текущей БД → прогнать миграцию → сверить,
   что число preference/playback/flow/mix-строк сохранилось до строки и **все**
   привязались к owner (ни одной с `user_id IS NULL`).
4. Смена PK и перелив данных — в **одной транзакции**; частично мигрированное
   состояние недопустимо.

### 3. Фильтрация всех запросов к персональным таблицам  ✅ РЕАЛИЗОВАНО

**Поверхность шире, чем казалось.** Прямые SQL-обращения к персональным
таблицам разбросаны по трём слоям (по grep, ~66 обращений всего):

- `app/store/*` — ~33 (mixes, playback, flow, release_aggregates, _helpers).
- `app/services/*` — ~21 прямых, из них **`services/dashboard.py` ~17 инлайн-SQL**
  прямо по `user_track_preferences` (history, listen_again,
  long_time_no_listen, discover_random и др.) — **не через store-методы**.
  Плюс `flow_candidates.py`, `flow_regions.py`.
- `app/api/*` — ~12 (mixes 7, map 3, navidrome 1, deps 1).
- **Движки скоринга персонализации** (тянут персональные store-методы, не
  инлайн-SQL, поэтому в grep выше не попали, но семантически персональны):
  `services/albums_for_you.py`, `services/release_scoring.py` — оба через
  `list_positive_track_ids_with_embeddings` (SEED вкуса: liked/score) и
  `list_release_track_preferences(release_id)`. **Сейчас эти два store-метода
  БЕЗ фильтра юзера → смешивают позитивные треки ВСЕХ юзеров в один профиль.**
  Это ядро персонализации — обязательно скоупить по `user_id`.

Вывод: нельзя ограничиться сигнатурами store-миксинов — **инлайн-SQL в сервисах
и роутерах тоже надо аудировать поштучно**. Каждый `SELECT/INSERT/UPDATE/DELETE`
по персональной таблице получает `user_id`. Это тот самый класс мест, где легко
пропустить (см. Доктрину) — гнать регресс-тест «A не видит B» на каждый.

- `_apply_playback_event_preferences` (`store/playback.py:669`) — **живой
  инкрементальный путь** обновления предпочтений на каждом событии (вызывается
  из `record_playback_event`, playback.py:588); писать/фильтровать по `user_id`.
- `recompute_user_preferences` (`store/mixes.py:630`) — full-rebuild утилита.
  **Проверено (grep): в `app/` не вызывается, только `tests/test_store.py`.**
  Сейчас делает `DELETE FROM user_*_preferences` **целиком** — в мультиюзере
  это стирает предпочтения ВСЕХ. Требование: метод **обязан** принимать
  `user_id` и удалять/пересобирать только `WHERE user_id = ?`; вариант «снести
  всё» физически недоступен из сигнатуры. Пока метод внешне не вызывается —
  ловить это должен тест, а не надежда, что путь не дёрнется.
- `record_playback_event` (`store/playback.py:520`) — писать `user_id`.
- `dashboard_shelf_response(store, key, ...)` (`services/dashboard.py`) и
  `ensure_dashboard_mixes_fast` — **11 шелфов дашборда** целиком персональные,
  сейчас без `user_id`. `get_flow_profile(settings.default_model)` в hero —
  глобальный синглтон → per-user (`(user_id, model_key)`).
- Каждый store-метод, читающий предпочтения/flow/миксы/плейлисты, принимает
  `user_id`. Меняет сигнатуры десятков методов и всех вызывающих роутеров/
  сервисов.

### 4. Проброс `user_id` от middleware до store  ✅ РЕАЛИЗОВАНО

- API-роутеры: сейчас `context()` (`api/deps.py:39`) отдаёт `(Store, Settings)`
  без пользователя. Ввести зависимость `current_user_id(request)` (читает
  `request.state.user_id`) и прокидывать в вызовы store.
- **✅ РЕШЕНО: делаем `UserScopedStore`/контекст-обёртку.** Ручной проброс
  `user_id` в ~66 обращений = 66 мест, где можно забыть, и каждый пропуск —
  молчаливая утечка; тест «A не видит B» ловит только покрытые методы. Раз
  сигнатуры десятков методов всё равно предстоит трогать, выгоднее один раз
  завести обёртку, которая несёт `user_id` и делает пропуск фильтра
  **невозможным по конструкции** (персональные методы недоступны без
  user-скоупа), чем 66 раз надеяться на внимательность. Решение принять **до**
  чекпоинта 3 — оно определяет его объём.

Реализация: auth middleware устанавливает request-local identity в
`ContextVar`, а `api/deps.py:context()` создаёт `Store` сразу с этим `user_id`.
Для service principal устанавливается явный `None`, поэтому персональные
store-методы отказывают, а не откатываются к owner. API-инвариант закреплён
двухсессионным тестом: плейлисты и playback-сессии Alice недоступны Bob даже
при обращении по известному ID, и наоборот.

### 5. Navidrome per-user  ✅ РЕАЛИЗОВАНО

Сейчас **лайки = звёзды сервисного аккаунта Navidrome**:
- `build_starred_track_ids(..., user=settings.navidrome.user)` (`api/playlists.py`),
  `sync_artist_liked_from_navidrome` — «liked» приходит из Navidrome starred.
- Скробл (`maybe_scrobble_navidrome_play`, `serializers/playback.py:240`) и
  star/unstar идут через `NavidromeClient(settings.navidrome)` — **единый
  админский аккаунт**.

**Решение:** per-user. Звёзды/скробл идут от имени каждого пользователя в его
Navidrome-аккаунт (креды = те, что он ввёл при логине).

**Наблюдение, снимающее вопрос хранения пароля at-rest:** и скробл, и
star/unstar происходят **только во время активной сессии** (скробл триггерится
playback-событием, звезда — кликом). Фоновой генерации flow/миксов
Navidrome-креды не нужны (считается по общим эмбеддингам). Значит пароль нужен
только на время жизни сессии, at-rest хранить не обязательно.

**Предложенная схема кредов (сохраняет модель безопасности Фазы 1):**

1. При логине шифруем пароль Navidrome ключом, **производным от сырого
   session-токена** (не от секрета в БД). Шифротекст кладём в строку `sessions`
   (новая колонка `nav_secret`).
2. В БД — только SHA-256 токена (как сейчас) + шифротекст. Утечка БД без сырого
   токена (он лишь в cookie у клиента) пароль не раскрывает. Открытого пароля
   at-rest нет нигде.
3. На каждый запрос: клиент шлёт сырой токен → выводим ключ → расшифровываем
   пароль → `NavidromeClient` от имени юзера для звезды/скробла.
4. Logout / протухание сессии → пароль исчезает вместе со строкой.
5. Первый логин (и опц. периодически): синк Navidrome starred юзера в его
   `user_track_preferences.liked` — тоже кредами из активной сессии.

Плюс: настоящий per-user Navidrome без пароля at-rest. Минус: без активной
сессии отложенных звёзд/скроблов нет — но их и не бывает (оба действия
интерактивные).

Затрагиваемые места: `serializers/playback.py:240` (scrobble),
`api/playlists.py:32` + `store/playback.py:1191` (starred sync/read),
все `NavidromeClient(settings.navidrome)` в интерактивных путях (star/unstar/
scrobble) → строить клиент из per-user кредов сессии, а не из `settings`.
Служебные пути (обложки, download, ping при логине, каталог-синк) остаются на
сервисном аккаунте `settings.navidrome`.

Криптопримитив ✅РЕШЕНО: **тянем `cryptography`** (AES). `hashlib`/`hmac` уже в
проекте, но симметричного шифра в stdlib нет; `cryptography` уже закладывался в
Фазе 1.5 под пароль Navidrome at-rest. Безопасность в приоритете.

Реализация: AES-GCM с уникальным nonce и ключом SHA-256 от сырого session-token;
credentials живут в request-local контексте. Интерактивные starred/star/unstar/
scrobble используют per-user client, первичный sync starred выполняется после
логина и повторяется при чтении Likes. Ошибка sync не отменяет успешный логин.

### 6. Фоновые процессы и воркер/бот  ✅ РЕАЛИЗОВАНО

**Масштаб (решено): ~3 юзера, генерим для всех, без урезания функционала.**
Новый аккаунт = полноценный опыт, идентичный текущему. Никаких тиров/деградации
для «неактивных». Значит ленивую генерацию как *обязательную оптимизацию* не
закладываем — при 3 юзерах flow/миксы генерим для всех. (Ленивость/TTL можно
оставить как задел, но не блокер и не режем ради неё UX.)

- `maintenance_loop` (`app/maintenance.py`) — тикает глобально. Flow-профили и
  генерация миксов сейчас — синглтоны (один `flow_profiles` на `model_key`).
  Per-user → N профилей/миксов: тик итерирует пользователей (`(user_id,
  model_key)` уникальность профиля). При 3 юзерах стоимость приемлема.
- Воркер анализа (`deploy/worker`) — работает с **общим** каталогом/эмбеддингами,
  его почти не трогаем (аудио-анализ не персональный). Но если появятся
  per-user фоновые задачи (сборка flow) — им нужен `user_id` в payload джобы.
- **Бот и плагин — вне контура, вопрос атрибуции снят.** Проверено: бот
  (`deploy/bot`) ходит по service-токену, но дёргает только `/health` и
  `/api/v1/navidrome/similar` (`discocs_bot/bot/services/discocs.py`) — чистый
  контент/каталог, **в персональные таблицы не пишет**, значит атрибутировать
  нечего. Плагин Navidrome **deprecated, будет удалён** — не закладываем.
  Единственный инвариант, который из этого остаётся (для §4): персональный
  эндпоинт, получивший запрос с принципалом `"service"` (без `user_id`),
  **обязан отказать**, а не писать в owner/NULL — при `UserScopedStore` это
  выходит по конструкции (нет `user_id` → метод недоступен).

### 7. UI  ✅ РЕАЛИЗОВАНО

- Индикатор текущего пользователя, выход (уже есть logout). Возможно — имя/
  аватар в шапке.
- Всё персональное (дашборд, лайки, flow, миксы, плейлисты) автоматически
  скоупится сервером по сессии — фронту менять запросы почти не нужно, но
  проверить, что нет клиентского кэша, шарящего данные между аккаунтами
  (react-query ключи, `playerStore`).
### 8. Глобальные операции — вне контура хостовых юзеров  ✅ РЕАЛИЗОВАНО

**Админ-роль в приложении не нужна.** Глобальные операции над общим каталогом
(`scan`, `analyze`, `build-index`, `navidrome-sync`, правка settings) делаются
через **старую админку** (`app/ui.html`, `:8711/admin`) с локалки без кредов —
это не часть публичного мультиюзер-контура.

Задача на уровне **деплоя, не приложения**: доменный nginx не должен
проксировать наружу порт бэкенда 8711, `/admin`, `/workers` и глобальные
job/settings-эндпоинты (в русле `docs/auth.md` → nginx-sample). Тогда хостовые
юзеры физически до них не дотягиваются, и роль/проверка в коде не требуется.

Реализация: frontend nginx возвращает 404 для `/admin`, `/api/map`,
`/workers`, глобальных `/jobs` и settings-эндпоинтов. Из job-семейства
наружу явно разрешены только per-user `albums-for-you` и `flow-profile`.
Backend `:8711` остаётся приватным LAN-контуром для старой админки и
удалённых workers и должен быть закрыт host firewall от интернета.

### 9. Регистрация и плейлисты  ✅ РЕАЛИЗОВАНО

**Регистрации нет.** Аккаунты в Navidrome заводит владелец вручную и раздаёт
креды. Значит:
- Нет формы регистрации, нет allowlist в приложении — контроль доступа = у кого
  есть Navidrome-креды (управляется на стороне Navidrome владельцем).
- `users` создаётся **автоматически при первом успешном логине** (upsert по
  navidrome_username). Это не «открытая регистрация» — впустить может только
  тот, кому владелец уже создал аккаунт в Navidrome.

**Плейлисты — per-user с полем видимости.** Задел уже есть: `CreatePlaylistDialog`
пишет `source_json.visibility` (`Public`/`Private`), поведения пока нет
(`plans/playlist.md:150,265`). Мультиюзер **включает это поведение**:
- `playlists` получает `user_id` (владелец) + видимость (из `source_json` или
  вынести в колонку `visibility`).
- `Private` — виден только владельцу; `Public` — виден всем юзерам (read-only
  для не-владельца). ❓уточнить: нужен ли `Shared`/соавторы — пока в
  `CreatePlaylistDialog` соавторов нет, вероятно не сейчас.
- Списки/шелфы плейлистов фильтруются: свои (любой видимости) + чужие public.
- Спец-плейлист Likes остаётся персональным и вне общего списка
  (`plans/playlist.md:274`).

### 10. Онбординг / стартовая инициализация профиля  📋 ОТЛОЖЕНО (Саня пропишет позже)

Не входит в базовый мультиюзер — прорабатывается и реализуется отдельно после
базы. Ниже — зафиксированная идея, чтобы контекст не потерялся.

При **первом входе** пользователя — экран инициализации вкусов, чтобы не
подкидывать полный рандом (у нового юзера пустой профиль предпочтений).

Идея (по образцу Deezer и др. стримингов):
- Сетка артистов; юзер выбирает ~10, которые ему нравятся.
- При выборе артиста рядом подгружаются ещё ~5 похожих на него (расширение
  выбора по одному клику).
- Результат → небольшая заготовка профиля предпочтений (seed-лайки артистов),
  с которой стартуют flow/рекомендации.

Открытые вопросы (продумать отдельно, до реализации):
- **Как выбирать артистов для сетки?** Логично по популярности — но данных о
  популярности у нас пока нет. Варианты: по числу треков в каталоге, по
  глобальным play_count (см. §исключение — но у новых юзеров и каталога он
  может быть пуст), по разнообразию жанров/эмбеддинг-кластерам (взять
  представителей разных регионов эмбеддинг-пространства — даёт покрытие вкусов
  без данных о популярности). Вероятно комбинация.
- **«Похожие 5»** — по артист-уровневой близости. Артист-эмбеддингов нет
  (`docs/data-model.md`: `artist_embeddings` не реализованы) → считать по
  центроиду треков артиста на лету или добавить артист-центроиды.
- **Как расширить инициализацию**, чтобы собрать более специфичные для нас
  данные (не только «нравится артист»)? — обсудить.
- Куда писать результат: seed в `user_artist_preferences` (liked/score) или
  отдельная bootstrap-таблица? Как это стыкуется с flow-профилем.
- Связано с `plans/recommendation-cards-flow.md` (концепт стартовой страницы/
  Flow) — держать согласованным.

**Требует отдельной проработки — не в первом заходе реализации.**

### 11. Неочевидные точки (доп. проход по коду)

Места, которые легко упустить — но без них мультиюзер протекает. Помечено
✅подтверждено / ❓проверить при реализации.

- **✅ Утечка на фронте через localStorage.** `ui/src/store/sessionPersistence.ts`
  персистит `discocs.sessionId.v1` и `discocs.playbackPosition.v1`. На одном
  браузере после logout юзера A / login юзера B восстановление потянет **чужую
  playback-сессию**. Нужно: (а) logout чистит эти ключи + весь react-query кэш
  и zustand-сторы (`playerStore`, `navidromeStore`, `uiStore`); (б) server-side
  restore-эндпоинт проверяет, что `session_id` принадлежит текущему `user_id`
  (иначе 403/пустой старт).
- **✅ Персональные данные в общей строке.** `release_aggregates` — глобальная
  строка на релиз (PK `release_id`, аудио-центроид), но
  `preference_summary_json` внутри неё — **личные** счётчики, причём сейчас
  собранные из `list_release_track_preferences(release_id)` **по ВСЕМ юзерам**
  (`services/release_scoring.py`, `services/albums_for_you.py`). Двойная
  проблема: агрегация по всем + хранение на общей строке. Нельзя: вынести
  preference-часть в per-user (таблица/кэш `(user_id, release_id)`) и считать
  по конкретному юзеру. Аудио-часть (`centroid_model`, `medoid_track_id`,
  `audio_summary_json`) остаётся общей.
- **✅ `albums_for_you_cache` — утечка.** Проверено: `get/set_albums_for_you_cache`
  ключуются по `model_name` only (`ON CONFLICT(model_name)`,
  `store/release_aggregates.py:213`). Персональный набор «альбомы для тебя»
  кэшируется без юзера → набор юзера A отдаётся B. PK → `(user_id, model_name)`.
- **✅ STATS_CACHE — безопасен.** Проверено: `stats(model)` (`api/jobs.py:113`)
  возвращает только каталожные счётчики (треки, эмбеддинги, индекс, агрегаты),
  персональных нет. Кэш по `model` оставить общим.
- **✅ Cache-Control — в целом ок.** Проверено: обложки/миксы/плейлист-обложки
  отдаются с `private, max-age=86400` (`api/mixes.py:141`, `api/playlists.py:251`,
  `services/cover.py`) — общие прокси не шарят. Персональные JSON-роутеры без
  cache-заголовков (браузер их агрессивно не кэширует). Публичного `max-age` на
  персональных данных нет. При доменном nginx — не ставить `proxy_cache` на
  персональные пути.
- **✅ autoplay-пул — session-scoped.** Проверено: пул хранится в
  `playback_sessions.state_json` (`autoplay.py:AUTOPLAY_POOL_STATE_KEY`), не в
  глобальном in-memory. Станет per-user автоматически, когда сессии получат
  `user_id`. Кандидаты (`generate_autoplay_candidates`) читают playback-события/
  предпочтения — их скоуп идёт из сессии + §3.
- **✅ Map-оверлеи — персональные.** Проверено: базовые 2D-координаты атласа
  общие, НО `api/map.py` оверлеит `list_generated_mixes`/`list_generated_mix_items`
  (dimension «Generated mix») и taste-region (flow) — это **личные** данные, их
  скоупить по `user_id`. Соседи (`get_map_track_neighbors`) используют только
  `feedback` (общий) — там ок.
- **✅ Фронт очищает identity state.** `logout()` даже при сетевой ошибке
  очищает React Query, persisted playback session/position, player queue и
  history, Media Session, liked IDs и transient dialogs. Device-настройки
  volume/mute/sidebar сохраняются. Глобальный обработчик 401 удаляет persisted
  playback до hard redirect. Profile popover явно показывает username.
  Instance-wide Navidrome settings убраны из public UI и остаются в приватной
  legacy admin.
- **❓ `MIX_GENERATION_LOCK`** — единый глобальный лок (`app/state.py`).
  Генерация миксов сериализуется между юзерами. При ~3 юзерах приемлемо, но при
  росте — узкое место; заложить возможность лока per-user.
- **❓ Спец-плейлист Likes** — источник = Navidrome starred текущего юзера;
  завязан на per-user Navidrome-креды (§5) и per-user preferences.
- **✅ `instant_mix_requests` — общая dev-телеметрия, вне контура.** Проверено:
  read-эндпоинт `/instant-mix/requests` (`api/mixes.py:227`) потребляет **только
  старая админка** (`app/ui.html:3429,3670`); новый UI (`ui/src`) его не читает.
  Значит по §8 он живёт за localhost-админкой и наружу не проксируется — как
  `feedback`, скоупить по юзеру не нужно. (Запись `user_id` в строку опц. —
  задел на будущее, не блокер.)
- **❓ SQLite write-contention** — больше юзеров = больше параллельных записей
  playback-событий в один SQLite. При ~3 юзерах ок (проект сознательно без
  Postgres до валидации качества, см. `CLAUDE.md`), но держать в уме как
  потолок масштабирования.
- **❓ Метрики** (`api/metrics.py`) — проверить при реализации, не отдаёт ли
  per-user данные без скоупа (вероятно каталожные/prom — низкий риск).
- **✅ Схема не может уезжать вперёд кода (найдено при реализации).** Смена PK
  preference-таблиц ломает существующие `ON CONFLICT(track_id)` upsert'ы, пока
  в код не прокинут `user_id` — т.е. «горизонтальный» ЧП2 (вся схема разом)
  завалил бы CI до ЧП3. Решение по реализации: катим **инкрементально**, чтобы
  каждый пуш был зелёным. **ЧП2a (сделано):** аддитивные nullable `user_id` на
  `playback_sessions`/`playback_events`/`flow_profiles`/`generated_mixes`/
  `playlists` + индексы + owner-backfill инфраструктура (`DISCOCS_OWNER_USER`,
  loud-fail без owner'а, идемпотентность, `VACUUM INTO`-бэкап, эвакуационная
  проверка счётчиков) — `StoreBase._migrate_owner_backfill`,
  `tests/test_multiuser_migration.py`. **Отложено:** PK-смена preference-таблиц
  и `albums_for_you_cache` едет вместе со скоупом их store-методов (вертикальный
  срез), чтобы upsert'ы не ломались в промежутке.

## Порядок реализации (черновой, разбить на чекпоинты)

1. **Личность:** таблица `users`, upsert при логине, `user_id` в сессии и
   middleware (`request.state.user_id`). Тесты на маппинг сессия→user.
2. **Схема + миграция:** `user_id` во все персональные таблицы, смена PK,
   перелив существующих данных на owner-юзера. Round-trip тесты.
3. **Store-слой:** ✅ `Store.for_user(user_id)` + фильтрация персональных
   методов, сервисного SQL и recommendation/cache путей. Изоляция закреплена
   двухпользовательскими регресс-тестами.
4. **API-слой:** ✅ request-local `current_user_id`, scoped store во всех
   роутерах. Двухсессионный API-тест исключает доступ по списку и прямому ID.
5. **Navidrome per-user:** ✅ AES-GCM шифр по сырому session-token, per-user
   клиент для starred/star/scrobble и синк starred на логине (§5).
6. **Глобальные агрегаты:** ✅ публичный `SUM(play_count)` для страницы артиста
   поверх per-user данных; track/release не добавляем до реальной потребности.
7. **Плейлисты visibility:** ✅ private видит только владелец; public читают и
   воспроизводят все, но изменяет только владелец; UI учитывает `editable` (§9).
8. **Фон:** ✅ maintenance итерирует scoped Store всех юзеров для albums/flow/
   миксов; background mix thread сохраняет `user_id`; service play-state sync
   отключён при multiuser auth, где credentials существуют только в сессии (§6).
9. **Деплой:** ✅ глобальные job/settings закрыты public nginx (§8).
10. **UI:** ✅ username indicator + полная очистка client identity state при
    logout/401; глобальные settings скрыты из public UI (§7, §11).
11. **Онбординг** (отдельно, после базового мультиюзера) — экран инициализации
    вкусов (§10). Сначала допроектировать.

Каждый чекпоинт: код + тесты + (при смене поведения) док. Пуш по завершении
чекпоинта, не всё разом (см. `CLAUDE.md`, checkpoint-пуши).

## Решённые вопросы

- **Identity:** свой внутренний `user_id` + маппинг на navidrome_username (§1).
- **Navidrome-лайки/скробл:** per-user; креды из активной сессии, шифр по
  токену, без пароля at-rest (§5).
- **Админ-роль:** не нужна; глобальные операции — в localhost-админке, вне
  публичного контура (§8).
- **Масштаб:** ~3 юзера, генерим для всех, полноценный опыт без урезания;
  ленивую генерацию как обязательную оптимизацию не закладываем (§6).
- **Owner-миграция:** все текущие данные привязать к owner'у (Саня) через env
  `DISCOCS_OWNER_USER`; если env не резолвится — миграция падает громко, без
  `user_id = NULL` (§2). Плюс предохранители миграции PK: бэкап, идемпотентность,
  эвакуационный тест, одна транзакция (§2).
- **Скоуп-обёртка:** делаем `UserScopedStore`/контекст, чтобы пропуск фильтра
  был невозможен по конструкции, а не ловился ревью; решить до чекпоинта 3 (§4).
- **`recompute_user_preferences`:** переводим на обязательный `user_id`
  (`DELETE ... WHERE user_id`), вариант «снести всё» недоступен; покрыть тестом,
  хоть путь сейчас и не вызывается из `app/` (§3).
- **Объём глобальных агрегатов:** пока **только артист** (§Исключение);
  трек/релиз — по факту потребности, `SUM() GROUP BY` на ~3 юзерах бесплатен,
  материализованный счётчик заранее не заводим.
- **Плейлисты Shared/соавторы:** **не сейчас** — private/public покрывает всё,
  задел в `source_json` двоичный; соавторство — отдельная фича с моделью прав.
- **`instant_mix_requests`:** общая dev-телеметрия (как `feedback`); read-путь
  только в localhost-админке, наружу не проксируется, per-user не нужен (§11).
- **Регистрация:** нет; аккаунты в Navidrome заводит владелец вручную. `users`
  auto-upsert при первом логине, без allowlist в приложении (§9).
- **Плейлисты:** per-user + поле visibility (private/public), включаем поведение
  существующего задела `source_json.visibility` (§9).
- **Глобальный агрегат:** счётчик прослушиваний на странице артиста —
  `SUM(play_count)` по всем юзерам, публичный (§Исключение).
- **`feedback`:** остаётся **общим** — это eval-сигнал качества алгоритма
  (оценка пары seed→result), не личный вкус.
- **Бот/плагин:** вне контура. Бот — отдельная сущность, читает только
  контент-эндпоинты (`/health`, `/navidrome/similar`), персональное не пишет —
  атрибутировать нечего. Плагин Navidrome deprecated, будет удалён. Инвариант
  §4: `service`-принципал без `user_id` на персональный эндпоинт → отказ (§6).
- **Криптопримитив:** тянем `cryptography` (AES) — симметричного шифра в stdlib
  нет; уже закладывался в Фазе 1.5. Безопасность в приоритете (§5).
