# Задача: оптимизация фронтенда и вылов «пожирателей ресурсов»

## Зачем этот документ

Это не разовый тикет, а **чеклист и методология**. Когда Саня скажет «оптимизируй
интерфейс» / «тормозит» / «жрёт память» — не отвечать «вроде всё ок» и не гадать.
Идти по этому документу, опираясь на **факты и замеры**, а не на интуицию.

Цель — находить код, который **тратит ресурсы (CPU, RAM, GPU, сеть) без
необходимости**: работа, которую можно не делать вообще, делать реже, или для
меньшего числа компонентов.

## Главное правило: факты, а не догадки

Прошлый раз мы долго тыкались вслепую (грешили на аудио-буфер, backend range,
GPU/шейдеры), пока не сняли **heap snapshot** — и он сразу показал причину.
Урок закреплён:

1. **Сначала измерить, потом чинить.** Не считать мегабайты на глаз.
2. Инструменты, которым верим:
   - **React DevTools Profiler** — кто и как часто ре-рендерится, «why did this render».
   - **Chrome DevTools → Performance** — flame chart, долгие задачи, layout thrash.
   - **Chrome DevTools → Memory (heap snapshot)** — что реально копится в куче.
   - **Chrome Task Manager (Shift+Esc)** — память процессов renderer/GPU.
   - **Network** — водопады, дубли, отсутствие кэша.
   - **Bundle analyzer** (`rollup-plugin-visualizer` для Vite) — размер и что грузится синхронно.
3. Воспроизвести проблему, снять метрику **до**, починить, снять **после**.
   Улучшение должно быть видно в цифрах, а не «кажется быстрее».

## Эталонный кейс (реальная найденная проблема)

**Симптом:** вкладка браузера уходила в OOM после 1–2 часов проигрывания.
Память росла ~2600 объектов/сек, только при воспроизведении, останавливалась на паузе.

**Корень (по heap snapshot):** ~1.65 млн объектов `PerformanceMeasure` (~198 МБ, 76% кучи).
React 19.2 dev-сборка эмитит `performance.measure()` на **каждый рендер каждого
компонента** (User Timing / Performance Tracks). Буфер не чистится → безграничный рост.

**Что раздувало счётчик — «шторм ре-рендеров»:**

- `<audio>` шлёт событие `timeupdate` ~4 раза/сек → `_setTime` →
  `set({ currentTime, duration })` в `playerStore` (без троттлинга).
- На `currentTime` подписаны **на верхнем уровне** сразу два всегда-смонтированных
  компонента: `PlayerBar` и `ExpandedPlayer`.
- `ExpandedPlayer` на каждый тик перерисовывал **всю очередь**:
  `queue.items.map(QueueItem)` + `autoplay_pool.map(QueueItem)` (~100+ штук).
- `QueueItem` **не мемоизирован** и каждый тянет Radix `DropdownMenu`
  (Popper/Menu/Provider) + 6 подписок на стор.
- Итог: ~100 items × ~6 Radix-подкомпонентов × 4/сек ≈ 2400 измерений/сек —
  ровно наблюдаемый рост.

**Почему это «пожиратель без необходимости»:** `currentTime` реально нужен только
двум мелочам — ширине прогресс-бара и подписи времени. Перерисовывать из-за него
очередь, меню, обложку, регуляторы — чистая потеря. `ExpandedPlayer` вообще
перерисовывался даже когда свёрнут и не виден.

Этот кейс — образец класса ошибок, который ищем ниже.

## Чеклист анти-паттернов (что искать)

### 1. Состояние, меняющееся часто, читается слишком высоко
- Высокочастотные значения (время трека, прогресс, курсор, скролл, ввод) должны
  жить в **самом мелком** компоненте, которому они нужны.
- Красный флаг: `useStore(s => s.currentTime)` в большом компоненте, где время
  влияет на один `<span>`.
- Красный флаг: обновление стора на каждый `timeupdate`/`scroll`/`mousemove`
  без троттлинга/`requestAnimationFrame`.

### 2. Компоненты, которые не размонтируются
- Оверлеи/панели, спрятанные через `translate`/`opacity`/`hidden` вместо
  условного рендера, продолжают жить и ре-рендериться.
- Красный флаг: тяжёлый компонент всегда в дереве, скрыт только классом.

### 3. Списки без мемоизации и виртуализации
- Элементы списков — `React.memo`; колбэки — стабильные (`useCallback`).
- Длинные списки (очередь, треки, результаты поиска) — виртуализировать
  (`@tanstack/react-virtual` уже в проекте).
- Красный флаг: `.map()` большого массива, где каждый элемент — тяжёлый
  (Radix-меню, обложка, много подписок).

### 4. Селекторы стора, возвращающие новую ссылку
- Селектор, возвращающий новый объект/массив каждый вызов, ломает мемоизацию и
  провоцирует ре-рендер на любое изменение стора.
- Красный флаг: `s => ({ a: s.a, b: s.b })` или `s => s.items.filter(...)`
  без `useShallow`/мемо.
- Много подписок на элемент × длинный список = сотни подписок на каждое
  изменение стора.

### 5. Утечки в эффектах
- Каждый `addEventListener`, `setInterval`, `setTimeout`, `requestAnimationFrame`,
  `ResizeObserver`, `IntersectionObserver`, WebGL-контекст — должен убираться в
  cleanup.
- Красный флаг: `useEffect` без функции очистки там, где заведён подписчик/таймер.
- Массивы, которые только растут и никогда не чистятся (напр. `playedHistory`).

### 6. Сеть: лишние и повторные запросы
- Дубли запросов, водопады (последовательно вместо параллельно), отсутствие
  кэша/дедупликации, рефетч на каждый ре-рендер.
- Красный флаг: `fetch` в компоненте без кэш-слоя; ключи кэша, меняющиеся каждый рендер.

### 7. Тяжёлый рендер и layout thrash
- Чтение геометрии (`getBoundingClientRect`) вперемешку с записью стилей в цикле.
- WebGL/canvas (`Plasma`, `PlasmaFBM`), анимации, `backdrop-filter`, большие blur —
  проверять, что не крутятся, когда не видны / на паузе.
- Картинки без явных размеров (layout shift), без `loading="lazy"`, без разумного
  `size=`.

### 8. Бандл
- Что грузится синхронно на старте; тяжёлые либы без code-splitting; роуты без
  ленивой загрузки. Прогонять bundle analyzer.

## Как действовать по запросу «оптимизируй / тормозит»

1. Уточнить симптом и **воспроизвести** его.
2. Снять базовую метрику подходящим инструментом (см. «факты, а не догадки»).
3. Локализовать по чеклисту выше — найти конкретный код.
4. Показать Сане список найденного с приоритетами (эффект × риск), **не чинить
   молча**.
5. Чинить по одному, с тестом/замером до-после. Правило проекта: тест на новый
   код, коммит после каждого изменения.

## Definition of Done для оптимизационной задачи

- Проблема описана фактом (метрика/снапшот/профиль), а не ощущением.
- Причина найдена в конкретном коде, не «в целом тяжело».
- Есть замер до и после, улучшение видно в цифрах.
- Нет регрессий поведения; тесты зелёные.
