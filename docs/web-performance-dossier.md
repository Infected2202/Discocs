# Досье: память и производительность нового Web UI

Статус: исследование, исправления ещё не начаты

Дата первичной фиксации: 2026-07-02

Область: новый UI в `ui/src/` (`:5173` / `/app`)

Старая админка `app/ui.html` в это исследование не входит.

## Зачем нужен этот документ

Во время воспроизведения трека вкладка Chrome начинает быстро наращивать память
и одновременно создаёт высокую нагрузку на CPU. Первичная диагностика выявила
крупный React render storm, однако пока нельзя считать доказанным, что он
объясняет весь рост нативной памяти renderer-процесса.

Этот документ разделяет:

- подтверждённые наблюдения;
- подтверждённые механизмы в коде;
- гипотезы, влияние которых ещё не измерено;
- проверки, необходимые до исправления;
- порядок будущих изменений и обязательные тесты.

Документ является рабочим журналом. После каждого эксперимента сюда нужно
добавлять дату, сценарий, результат и изменение уровня уверенности.

## Краткий вывод

Сейчас подтверждена следующая цепочка:

1. `HTMLAudioElement.timeupdate` обновляет `currentTime` в глобальном Zustand
   store.
2. `ExpandedPlayer` подписан на `currentTime` на верхнем уровне.
3. При каждом обновлении React заново проходит всё дерево расширенного плеера,
   включая всю очередь, элементы Radix UI и их providers.
4. Плеер остаётся смонтированным даже в закрытом состоянии: он только
   сдвигается за пределы экрана через CSS transform.
5. React 19.2 development build создаёт Performance Track entries для
   отрендеренных компонентов.
6. В исследованном сеансе создавалось около 2635 `PerformanceMeasure` в секунду.
7. Heap snapshot содержал 1 647 980 таких объектов, удерживавших около 198 МБ
   JS heap без учёта всей связанной нативной памяти Chromium.

Это доказанная серьёзная проблема. Одновременно остаются открытыми два вопроса:

- объясняет ли React instrumentation весь рост `Private Data` примерно на
  895 МБ, либо параллельно растут аудиобуферы Chromium;
- воспроизводится ли рост с той же скоростью в production build, где React
  Performance Tracks по умолчанию отключены.

## Шкала уверенности

| Уровень | Значение |
|---|---|
| A — подтверждено | Есть прямое runtime-измерение или детерминированный вызов в коде |
| B — сильное свидетельство | Механизм виден в коде, но реальный вклад ещё не измерен отдельно |
| C — гипотеза | Правдоподобно, но необходим контрольный эксперимент |
| D — пониженный приоритет | Проверка или наблюдение противоречат гипотезе как главной причине |

## Исходные симптомы

Наблюдения пользователя:

- рост памяти начинается при воспроизведении трека;
- замечена корреляция скорости роста с битрейтом;
- отключение шейдеров не меняет скорость роста памяти;
- reload страницы не сразу возвращает память операционной системе;
- после reload запуск другого трека меняет картину освобождения памяти;
- проблема наблюдалась при закрытом расширенном плеере.

Ограничения этих наблюдений:

- скорость роста в МБ/мин пока не записывалась;
- не записаны битрейт, sample rate, число каналов и длительность контрольных
  треков;
- dev и production build пока не сравнивались;
- между сценариями не всегда создавался новый renderer-процесс;
- корреляция с битрейтом пока не отделена от длительности трека, размера
  очереди и других параметров сессии.

## Карта найденных проблем

### WEB-PERF-001: `currentTime` инвалидирует весь `ExpandedPlayer`

Уверенность: **A — подтверждено**

Приоритет: **P0**

Код:

- `ui/src/components/player/ExpandedPlayer.tsx:42` — подписка на `currentTime`;
- `ui/src/components/player/ExpandedPlayer.tsx:335` — рендер всей очереди;
- `ui/src/components/player/ExpandedPlayer.tsx:354` — рендер autoplay pool.

Механизм:

```text
audio timeupdate
  -> playerStore._setTime()
  -> ExpandedPlayer render
  -> queue.items.map()
  -> QueueItem
  -> Radix DropdownMenu / Popper / Providers
  -> React 19.2 Performance Track entries
```

Важно: 2635 entries/сек не означают 2635 отдельных store updates. Вероятная
картина — несколько `timeupdate` в секунду, каждое из которых проходит сотни
компонентов.

Подтверждено:

- runtime-имена entries совпадают с компонентами очереди;
- скорость создания измерена;
- top-level подписка и полный обход очереди видны в коде.

Не подтверждено:

- точное число commits и renders в секунду;
- доля роста `Private Data`, приходящаяся на этот механизм;
- поведение production build.

Критерий исправления:

- изменение только `currentTime` не должно рендерить `QueueItem`;
- число React measure entries при воспроизведении должно снизиться минимум на
  95% в сопоставимом dev-сценарии;
- очередь не должна появляться в React Performance track при обычном тике
  времени.

Обязательный тест:

- смонтировать плеер с несколькими QueueItem;
- изменить в store только `currentTime`;
- доказать, что render spy QueueItem не был вызван повторно;
- отдельно доказать обновление progress/time leaf-компонентов.

### WEB-PERF-002: закрытый `ExpandedPlayer` остаётся активным

Уверенность: **A — подтверждено**

Приоритет: **P0**

Код:

- `ui/src/components/player/ExpandedPlayer.tsx:104-108`;
- `ui/src/components/layout/AppShell.tsx:73`.

Закрытое состояние реализовано через:

Runtime-измерение 2635 entries/сек было получено при визуально закрытом плеере.

Необходимо сохранить exit-анимацию, поэтому простое немедленное `return null`

- либо используется отдельная lifecycle-модель, которая не обрабатывает
  playback updates в hidden-состоянии.

Критерий исправления:

- после завершения close transition в DOM нет QueueItem расширенного плеера;
- закрытый плеер не подписан на `currentTime`;
- повторное открытие корректно восстанавливает актуальное состояние.

Обязательные тесты:

- после close transition QueueItem размонтированы;
- обновление времени в закрытом состоянии не рендерит содержимое;
- open/close не ломает выбранную mobile tab семантику либо её reset явно

### WEB-PERF-005: строки каталога подписаны на сырые глобальные playback fields

Уверенность: **B — сильное свидетельство**

Приоритет: **P1**

Код:

- `ui/src/components/media/TrackRow.tsx:44-45`;
- `ui/src/components/media/VirtualTrackRow.tsx:36-37`.

Каждая строка читает полные `currentTrackId` и `playbackState`. При смене ID
selector каждой строки получает новое число, поэтому обновляются все строки,
хотя визуально изменились только старая и новая активная строки. При play/pause
обновляются также все строки, хотя результат важен только текущей.

Предпочтительные selectors:

```text
isActive = state.currentTrackId === track.id
isPlaying = state.currentTrackId === track.id
            && state.playbackState === "playing"
```

Проверка и тест:

- несколько строк с render spies;
- смена active track рендерит только старую и новую строку;
- play/pause рендерит только активную строку.

### WEB-STATE-006: refill при skip запускается дважды

Уверенность: **A — подтверждено кодом**

Приоритет: **P1**

Код:

- `ui/src/store/playerStore.ts:329` вызывает `recordEvent("skipped")`;
- `recordEvent()` после успешного post вызывает
  `scheduleAutoplayRefill(eventType)`;
- `ui/src/store/playerStore.ts:340` повторно вызывает
  `scheduleAutoplayRefill("skipped")`.

Следствие: один skip способен запустить два параллельных refill pipeline.

Реальное влияние на память и сеть пока не измерено. Детерминированность двойного
вызова нужно сначала закрепить failing-тестом.

Обязательный тест:

- один `skipNext()` отправляет один feedback event;
- один `skipNext()` запускает ровно один refill;
- переход на следующий item остаётся одинарным.

### WEB-STATE-007: конкурентные refill могут применять ответы в другом порядке

Уверенность: **B — сильное свидетельство**

Приоритет: **P1**

`scheduleAutoplayRefill()` не имеет:

- in-flight lock;
- deduplication;
- generation/session token;
- отмены устаревшего запроса.

После `await refill...` выполняется `get().refreshQueue()`, который читает уже
текущее состояние store. Несколько feedback событий или смена source во время
запроса способны создать лишние refresh и потенциально применить состояние не
в ожидаемом порядке.

Необходимо выбрать семантику:

- один refill in flight и один trailing refill;
- либо generation token с игнорированием устаревшего результата.

Обязательные тесты:

- два быстрых события не создают параллельные refill-запросы;
- устаревший результат предыдущей session не меняет новую session;
- ошибка refill не блокирует последующий refill.

### WEB-GPU-008: WebGL render loops живут постоянно

Уверенность: **A для факта RAF, D как главная причина исследуемой памяти**

Приоритет: **P2 для памяти, P1 для CPU/энергопотребления**

Код:

- `ui/src/components/layout/AppShell.tsx:48` — полноэкранный `PlasmaFBM active`;
- `ui/src/components/player/PlasmaFBM.tsx:221`;
- `ui/src/components/player/Plasma.tsx:272`.

Оба renderer планируют следующий `requestAnimationFrame` безусловно. Если
`active=false`, GPU draw можно пропустить, но callback всё равно вызывается
каждый frame. Основной фон передаётся как `active` всегда.

Пользователь проверил, что отключение шейдеров не меняет рост памяти. Поэтому
шейдеры не считаются корнем текущей утечки. Однако высокая CPU/GPU-нагрузка
остаётся отдельной подтверждаемой проблемой.

Проверка:

- Chrome Performance recording на 30 секунд;
- сравнить scripting/GPU time с включёнными и отключёнными renderer;
- проверить paused, hidden tab и `prefers-reduced-motion`.

Критерий исправления:

- при inactive нет постоянного RAF;
- при hidden document анимация приостанавливается;
- один renderer не создаётся повторно при смене трека;
- WebGL resources освобождаются при реальном unmount.

### WEB-MEM-009: `playedHistory` растёт и нигде не используется

Уверенность: **A для факта, C для заметного влияния**

Приоритет: **P2**

Код:

- `ui/src/store/playerStore.ts:56`;
- `ui/src/store/playerStore.ts:115-123`;
- других чтений `playedHistory` в UI нет.

Массив хранит полные QueueItem и сбрасывается только при создании новой source
session. В очень долгой сессии это гарантированный линейный рост, но он не
объясняет быстрый рост внутри одного трека.

Решение после подтверждения требований:

- удалить client history полностью;
- либо хранить только ID в ограниченном ring buffer;
- либо использовать server-provided `queue.played`.

### WEB-IMG-010: маленькие обложки могут запрашивать исходное изображение

Уверенность: **C — гипотеза**

Приоритет: **P2**

`ArtworkImage.size` задаёт CSS dimensions, но не переписывает URL. QueueItem
передаёт `size={36}`, однако фактический network resource зависит от URL,
пришедшего с backend.

Chrome Task Manager показывал около 142 МБ image cache. Это не главный объём,
но вклад заметный.

Проверка:

- Network panel: decoded/body size URL обложек QueueItem;
- проверить наличие `size=` в backend URL;
- сравнить image cache при очереди 20 и 500 элементов;
- повторить после виртуализации.

Нельзя исправлять до проверки: backend уже может возвращать оптимизированный
URL.

### WEB-LIFE-011: неполный cleanup временных listeners, timers и animations

Уверенность: **B для механизма, C для реального влияния**

Приоритет: **P2**

Кандидаты:

- window `mousemove`/`mouseup` listeners в volume drag;
- window listeners в seek drag;
- `VolumeControl.hideTimer`;
- `animateScroll()` без cancel handle.

В обычном завершённом interaction listeners удаляются. Утечка возможна, если
компонент размонтируется во время drag/animation. Это не объясняет текущий
непрерывный рост при простом воспроизведении.

Тесты:

- unmount во время drag удаляет listeners;
- unmount во время scroll animation отменяет RAF;
- fake timers не вызывают setState после unmount.

### WEB-TEST-012: проект использует два несовместимых тестовых контура

Уверенность: **A — подтверждено запуском**

Приоритет: **P1 до рефакторинга**

- добавить её в документацию и CI.

### WEB-AUDIO-013: вклад нативного медиапайплайна пока не исключён

Уверенность: **C — открытая гипотеза**

Приоритет: **P0 для диагностики**

`AudioEngine.load()` уже:

- останавливает старый element;
- очищает `src`;
- вызывает `load()`;
- создаёт новый `Audio`.

Это покрыто unit-тестами. Кроме того, рост наблюдается во время одного трека,
поэтому накопление старых Audio elements не выглядит достаточным объяснением.

Однако остаются варианты:

- encoded network data удерживается до конца трека;
- decoder/PCM buffers растут;
- Chrome не возвращает освобождённые allocator pages ОС;
- React entries и media buffers растут одновременно.

Корреляция с битрейтом не согласуется напрямую с одним только React render
storm, потому что частота `timeupdate` обычно не должна линейно зависеть от
битрейта. Это сильная причина не закрывать медиагипотезу преждевременно.

## Контрольные эксперименты

### EXP-001: dev против production

Цель: отделить React 19.2 development instrumentation от продуктового
поведения.

Сценарий:

1. Выбрать один трек и одну фиксированную очередь.
2. Создать новый renderer-процесс.
3. Запустить dev build на 15 минут.
4. Записывать каждые 60 секунд:
   - tab memory footprint;
   - JS active memory;
   - VMMap Private Data committed;
   - количество `PerformanceMeasure`;
   - CPU;
   - playback position.
5. Повторить с `vite build` + `vite preview`.

Интерпретация:

- production стабилен, dev растёт — основная утечка связана с Performance
  Tracks, но render storm всё равно исправляется;
- оба растут сходно — медиапайплайн или другая нативная память остаётся главным
  кандидатом;
- production растёт медленнее, но не стабилен — вероятны две независимые
  причины.

### EXP-002: очистка Performance entries во время воспроизведения

Цель: оценить вклад entries без изменения приложения.

Сценарий:

1. Новый renderer-процесс.
2. Начать воспроизведение.
3. Первые 5 минут ничего не очищать.
4. Следующие 5 минут вызывать `performance.clearMeasures()` каждые 10 секунд.
5. Сравнить slope VMMap Private Data.

Ограничение: очистка entries меняет исследуемую систему и не обязана немедленно
возвращать committed pages ОС. Поэтому важен slope, а не мгновенное падение.

### EXP-003: контроль render fan-out

Цель: измерить число React work units на один `timeupdate`.

Сценарии:

- expanded=false, очередь 20/100/500;
- expanded=true, очередь 20/100/500;
- PlayerBar отдельно;
- после будущей изоляции clock leaf-компонентов.

Метрики:

- entries/сек;
- commits/сек;
- render count QueueItem;
- scripting time;
- heap allocation rate.

### EXP-004: проверка корреляции с аудиопараметрами

Цель: проверить заявление о битрейте без смешения факторов.

Нужны треки одинаковой или близкой длительности:

- низкий compressed bitrate;
- высокий compressed bitrate;
- lossless;
- по возможности одинаковые sample rate и channel count.

Для каждого запуска:

- новый renderer;
- одинаковая очередь;
- одинаковое expanded state;
- shaders одинаково включены или выключены;
- записать bitrate, sample rate, channels, duration;
- измерить МБ/мин после первых двух минут warmup.

Подсказки для интерпретации:

- slope около `bitrate / 8` указывает на удержание encoded data;
- slope, близкий к PCM rate, сильнее указывает на decoded buffers;
- одинаковый slope при разных аудиопараметрах указывает на UI/instrumentation.

### EXP-005: минимальный audio-only control

Цель: отделить Chromium media pipeline от React UI.

Временный диагностический entry point:

- один `new Audio(url)`;
- без Zustand;
- без React player components;
- без artwork и shader;
- только play/pause и текстовая позиция.

Если тот же трек растит Private Data с сопоставимым slope, исследование
переключается на delivery/range requests/Chrome media pipeline. Если рост
исчезает, приоритет остаётся у React/UI.

Диагностический entry point не должен попадать в production bundle без явной
необходимости.

### EXP-006: image cache

Цель: измерить реальный вклад обложек.

- записать число image requests и transfer/decoded size;
- закрытый и открытый expanded player;
- очередь 20/100/500;
- до и после виртуализации;
- проверить, освобождается ли image cache после размонтирования.

## Условия закрытия расследования

Расследование можно считать завершённым только когда:

- production memory после warmup выходит на плато либо остаётся в заранее
  согласованном ограниченном диапазоне;
- dev build больше не создаёт тысячи React entries в секунду;
- тик времени не рендерит очередь и статические controls;
- закрытый expanded player не держит тяжёлое активное дерево;
- refill не дублируется и не применяет устаревшие результаты;
- paused/hidden UI не выполняет постоянную графическую работу;
- полный UI test command действительно запускает component и store tests;
- корреляция с битрейтом либо воспроизведена и объяснена, либо опровергнута
  контролируемым экспериментом.
