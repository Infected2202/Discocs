# Инструменты рабочей машины

Часть инструментов из `tools/` работает только на ПК с GPU: `describe` (описания лейблов — локальная модель в
LM Studio, поиск SearXNG) и `music-fill` (свой веб-интерфейс). Управляются они из админки discocs: раздел
«Инструменты» ставит задачи, а воркер на ПК (`tools/agent`) их выполняет.

## Кто к кому ходит

Воркер ходит в discocs сам, discocs к ПК не подключается: на ПК не открываются порты, LM Studio не выставляется
в сеть. Воркер ждёт задачу **долгим опросом** — запрос `poll` висит на сервере до минуты, пока задачи нет, — так
что в простое воркер не тратит ни процессор, ни сеть. Авторизация — сервисный токен (`X-Discocs-Service-Token`,
см. `docs/auth.md`), как у остальных воркеров.

Воркер на связи, если опрашивал не дольше 90 секунд назад (`WORKER_ONLINE_SECONDS`).

## Задачи

`tool_jobs`: `tool` (`describe` / `music-fill`), `action`, `params_json`, `status`
(`queued` → `running` ⇄ `paused` → `done` / `failed` / `cancelled`), `control` — чего хочет админка
(`run` / `pause` / `cancel`), `progress_json`, `message`, `worker_id`.

- Воркер берёт свою незаконченную задачу (он перезапустился) или самую старую в очереди среди инструментов,
  которые он умеет.
- Пауза и отмена из админки доходят до воркера ответом на его прогресс. Задачу, которую некому подтвердить, отмена
  закрывает сразу: ещё никто не взял, воркер не на связи или воркера нет вовсе (прогон из командной строки,
  переведённый в running руками). Закрытая задача не оживает от запоздалого прогресса.
- `describe` — одна задача одновременно. Список лейблов фиксируется при создании (`params.label_ids`, крупные
  первыми); воркер берёт их порциями (`describe/next`), итог по каждому присылает сразу. Перезапущенный воркер
  получит недоделанные снова.
- `music-fill` — команды `start` / `stop` сервера на ПК; состояние сервера воркер присылает в `state`.

## Какие лейблы берёт describe

| scope | лейблы |
|---|---|
| `missing` | без описания |
| `replace` | без описания или с найденным синхронизацией (Википедия, Discogs, Beatport) |
| `not_found` | где агент уже пробовал и ничего не нашёл; воркер прогоняет их вторым проходом (`tools/describe/rescue.py`): лейбл только на сборниках узнаётся по названию, вместо пустоты — короткая справка |
| `ids` | выбранные (перегенерация из админки) |

Плюс `min_releases` — порог по числу релизов в библиотеке. Никогда не берутся лейблы с редакционным описанием и
самовыпуски (`label_sync_state.status = self_released`: «Independent», «Not On Label»). В `missing` и `replace` не
берутся лейблы, о которых агент уже ничего не нашёл, — их перебирает отдельный запуск `not_found`.

## Итоги агента

Текст агента сразу становится описанием лейбла (`description_source = agent`) — тысячи текстов вручную не
вычитать. Защита:

- редакционное описание агент не трогает (итог `skipped`);
- «ничего не нашлось» прежнее описание не стирает, в том числе прежний текст агента;
- синхронизация лейблов текст агента не перезаписывает; при склейке лейблов весомее описание `editorial`, затем
  `agent`, затем найденное синхронизацией — запись агента переезжает вместе с текстом;
- прежнее описание хранится в `label_agent_descriptions.previous_*`: «откатить» возвращает его (текст агента
  поверх текста агента откатывается к тому, что было до агента).

На странице лейбла текст агента, как и редакционный, идёт без подписи «Источник». Модель, дата и страницы, из
которых взяты факты, видны только в админке.

## Админка

Раздел **Tools** старой админки (`/admin?view=tools`, обновляется раз в 5 секунд):

- состояние воркера: на связи ли, загружена ли модель, сколько видеопамяти занято;
- music-fill: запущен ли сервер (и кем — воркером или руками), кнопки «Start server» / «Stop server», ссылка;
- describe: покрытие (лейблы, с описанием по источникам, без описания по числу релизов, итоги агента), запуск
  (какие лейблы и порог по релизам), текущая задача — прогресс-бар по итогам на сервере, сколько написано / не
  найдено / упало, скорость и сколько осталось, какие лейблы в работе и на каком шаге, пауза (в том числе
  «GPU занят — модель выгружена») / продолжить / отмена. Статус задачи пишет воркер, поэтому админка сверяет его
  с тем, на связи ли воркер (`worker_online`, `worker_seen_at` в `GET /tools/describe`): воркер пропал — «not
  running: the worker is offline, last seen …», а не «running»; пауза и отмена, пока воркер их не подтвердил, —
  «pausing» / «cancelling»;
- последние тексты агента для выборочного просмотра: текст, источники фактов, «Regenerate» (задача describe на
  один лейбл) и «Revert».

Воркер — `tools/agent` (см. его README): долгий опрос, приоритет «ниже обычного», модель в LM Studio только на
время задачи, пауза и выгрузка модели, когда видеопамять занята игрой.

## API

Воркер:

| запрос | что |
|---|---|
| `POST /api/v1/tools/workers/{id}/poll` `{tools, state, wait}` | состояние воркера; ждать задачу до `wait` секунд → `{job}` или `{job: null}` |
| `POST /api/v1/tools/jobs/{id}/progress` `{status?, progress?, message?}` | прогресс → `{control}` |
| `POST /api/v1/tools/jobs/{id}/describe/next` `{limit, exclude}` | следующие лейблы с артистами, релизами и внешними id из библиотеки |
| `POST /api/v1/tools/describe/results` `{job_id, label_id, status, description?, sources?, model?, note?}` | итог по лейблу → `{outcome}` |

Админка:

| запрос | что |
|---|---|
| `GET /api/v1/tools` | воркеры (`online`, `state`) и последние задачи |
| `POST /api/v1/tools/jobs` `{tool, action, scope?, min_releases?, label_ids?}` | поставить задачу; describe уже идёт — 409, лейблов нет — 400 |
| `POST /api/v1/tools/jobs/{id}/control` `{control}` | пауза / продолжить / отмена |
| `GET /api/v1/tools/describe` | покрытие описаниями, текущая задача (`counts` — сколько лейблов с итогом, по итогам на сервере), последние тексты агента |
| `POST /api/v1/tools/describe/{label_id}/revert` | вернуть описание, бывшее до агента |

Покрытие (`stats`) считается по лейблам с релизами в библиотеке, самовыпуски — отдельно: сколько с описанием и из
каких источников, сколько без описания по числу релизов (1 / 2 / 3+), сколько можно заменить, итоги агента.
